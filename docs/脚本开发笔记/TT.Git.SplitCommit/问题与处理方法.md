## 问题 1：PS 5.1 管道编码转换损坏中文内容

**现象**：代码页 936（GBK）环境下，`git diff --cached` 输出的中文内容经 PS 管道后损坏

**根因**：PS 5.1 管道按系统代码页（936）解码 git 的 UTF-8 输出，导致中文乱码

**处理方法**：
- 所有 git 输出一律通过 .NET Process 字节流读取（`RunGitBytes`）
- 用 `UTF8Encoding` 解码字节数组
- 不使用 `git ... | ForEach-Object` 或 `$(git ...)` 等管道写法

```powershell
# ❌ 错误：PS 管道按 CP936 解码
$lines = git diff --cached --name-only

# ✅ 正确：.NET Process 字节流 + UTF-8 解码
$bytes = __GitSplit_RunGitBytes -Arguments "diff --cached --name-only"
$content = $utf8NoBom.GetString($bytes)
```

## 问题 2：`git rev-parse --show-toplevel` 中文路径乱码

**现象**：中文路径仓库（如 `新疆业务网关\xjyw_intf_srd`）下，`git rev-parse --show-toplevel` 输出乱码

**根因**：git 输出中文路径时受系统代码页影响，即使通过 .NET Process 字节流读取也无法保证正确

**处理方法**：改用纯文件系统查找 `.git` 目录，不经过 git 输出

```powershell
function __GitSplit_FindRepoRoot {
    $dir = (Get-Location).Path
    while (-not [string]::IsNullOrEmpty($dir)) {
        if (Test-Path (Join-Path $dir '.git') -PathType Container) { return $dir }
        if (Test-Path (Join-Path $dir '.git') -PathType Leaf) { return $dir }
        $parent = Split-Path $dir -Parent
        if ($parent -eq $dir) { break }
        $dir = $parent
    }
    return ''
}
```

## 问题 3：PS 5.1 空数组跨函数展平为 `$null`

**现象**：空暂存区时报"无法获取暂存区文件列表"（应报"暂存区为空"）

**根因**：PS 5.1 经典陷阱——函数返回空数组 `@()` 或空 `byte[]`（长度为 0）时，PowerShell 管道会将其**展平为 `$null`**。调用者用 `$null -eq $result` 检测失败，但实际命令执行成功

**处理方法**：所有返回数组的函数添加逗号前缀 `return ,$array`，防止管道展平

```powershell
# ❌ 错误：空数组被展平为 $null
return $bytes          # $bytes 长度为 0 时，调用者收到 $null
return @()             # 调用者收到 $null

# ✅ 正确：逗号前缀防止展平
return ,$bytes
return ,@()
```

**受影响函数**（共 10 个）：
`RunGitBytes`、`RunGitNameLines`、`GetDiffLines`、`GetDiffLinesFull`、`ParseHunks`、`SplitSingleHunk`、`SplitFileByHunks`、`ParseEolsFromBytes`、`GreedyPack`、`GetStagedContentBytes`

## 问题 4：`git apply --cached` 不支持 `-U0` 格式 patch

**现象**：尝试用 `git apply --cached` 应用 `-U0` 格式的 patch 时失败

**根因**：`git apply --cached` 对 `-U0` 格式的支持有限

**处理方法**：改用 `git hash-object -w` + `git update-index --cacheinfo` 方案
1. 将 hunk 应用到 HEAD 内容，生成中间状态字节
2. 写入临时文件，`git hash-object -w` 创建 blob
3. `git update-index --add --cacheinfo` 更新暂存区

## 问题 5：index.lock 竞态条件

**现象**：快速连续执行 `git update-index` 和 `git commit` 时，前一个操作可能未完全释放 `index.lock`，导致后续操作失败

**处理方法**：
- 主流程 `git reset` 前检查并清理残留 `index.lock`
- `CommitFiles` 和 `CommitHunks` 中 `update-index` 和 `commit` 失败时清理 lock 并重试一次
- 重试前 `Start-Sleep -Milliseconds 200` 等待 lock 释放

```powershell
if ($LASTEXITCODE -ne 0) {
    $cleaned = __GitSplit_CleanIndexLock
    if ($cleaned) {
        Start-Sleep -Milliseconds 200
        # 重试 git 命令...
    }
}
```

## 问题 6：hunk 切分提交改变文件编码（BOM 丢失、CRLF→LF）

**现象**：hunk 切分提交后，文件编码从 UTF-8 BOM 变为无 BOM，行尾从 CRLF 变为 LF

**根因**：`ApplyHunksToContent` 未保留原始文件的 BOM 和逐行行尾格式

**处理方法**：
- **BOM 保护**：`ApplyHunksToContent` 入口检测 BOM（前 3 字节 `EF BB BF`），出口恢复
- **行尾保护**：逐字节扫描行尾类型，行操作时行尾与内容绑定；BOM + CRLF/LF 混用均可保留

> 注意：问题 6 的 BOM 保护初版只做了"出口恢复"，遗漏"入口剥离"，导致带 BOM 文件在真实提交时 BOM 重复（见问题 12）。

## 问题 7：`SplitSingleHunk` 后续子 hunk 的 OldStart 计算错误

**现象**：行级切分后，后续子 hunk 的行顺序错乱

**根因**：后续子 hunk 的 `OldStart` 使用"新内容行号"（`oldStart + prevAddLines`），而 `ApplyHunksToContent` 累积模式将其当作"旧行号"处理

**处理方法**：改为基于旧行号参考系
- 修改型：`OldStart = oldStart + oldCount - 1`（旧行最后一行之后）
- 新增型：`OldStart = 0`（旧行不存在）

## 问题 8：纯插入型子 hunk 行尾继承不准确

**现象**：混用 CRLF/LF 文件，hunk 切分提交后部分行行尾不正确

**根因**：纯插入型 hunk 只能从前一行继承统一行尾，无法区分目标文件中各行实际的不同行尾

**处理方法**：两层保护
1. **EolHints**：从暂存区目标文件解析逐行行尾，附加到子 hunk（最准确）
2. **pendingEols 队列**：替换型 hunk 删除旧行时，被新行未覆盖的旧行行尾入队，供后续纯插入型取用

## 问题 9：`>` 重定向和 `Out-File` 默认 UTF-16 LE

**现象**：用 `>` 重定向保存文件后，git 无法正确解析（编码不匹配）

**根因**：PS 5.1 的 `>` 和 `Out-File` 默认使用 UTF-16 LE 编码

**处理方法**：写入文件时统一使用 `[System.IO.File]::WriteAllBytes()`

```powershell
# ❌ 错误：默认 UTF-16 LE
$content | Out-File $tempFile
$diff > $backupFile

# ✅ 正确：字节写入
[System.IO.File]::WriteAllBytes($tempFile, $contentBytes)
```

## 问题 12：带 BOM 文件 hunk 切分提交后 BOM 重复（首行内容损坏）

**现象**：修改一个**已存在且带 BOM** 的文件做 hunk 切分提交后，最终 HEAD 内容与原始 staged 内容不一致——首行前多出一个 BOM（字节层面为 `EF BB BF` 重复），git diff 显示首行 `?` 前缀，工作区出现 ` M` 状态。

**根因**：`ApplyHunksToContent` 在处理带 BOM 的 HEAD 内容时，**只在出口恢复 BOM，没有在入口剥离输入 BOM**：
1. 入口检测到 `$hasBom = true`
2. 但 `$content = $utf8NoBom.GetString($HeadBytes)` 未剥离 BOM，BOM 被 `UTF8Encoding` 解码成 `U+FEFF` 字符，**当作第一行内容**参与解析
3. 重建内容时（"恢复 BOM"逻辑）又加回一次 BOM
4. 结果：BOM 被保留两次 → 双重 BOM

**引入时机**：提交 `d341b10`（2026-08-14 19:21）新增"检测 BOM + 恢复 BOM"逻辑时，只补了输出未补输入剥离，造成遗漏。此前 `429cc7c`（引入 `ApplyHunksToContent`）虽无剥离，但也不做 BOM 恢复，因此不会重复。

**影响范围**：仅影响**修改已有带 BOM 文件**的 hunk 切分提交；新增文件（HEAD 为空，`$isNewFile`）和多行纯文本提交不受影响。故此前 `-MaxBytes` 常规使用可能一直未暴露。

**处理方法**：入口检测到 BOM 后，先**剥离（起始偏移 3）再解析**，重建时仍按 `$hasBom` 恢复，保证 BOM 恰好一次。

```powershell
# ❌ 错误：BOM 被当第一行内容，重建又加回 → BOM 重复
$content = $utf8NoBom.GetString($HeadBytes)

# ✅ 正确：检测到 BOM 先剥离（偏移 3），重建时按 $hasBom 恢复
$content = if ($hasBom) {
    $utf8NoBom.GetString($HeadBytes, 3, $HeadBytes.Length - 3)
} else {
    $utf8NoBom.GetString($HeadBytes)
}
```

**验证方法**：对带 BOM 的已有文件做多 hunk 切分提交后，对比 `git rev-parse HEAD:file` 与原始暂存 blob hash 是否一致，并检查工作区是否干净。
